# 人员逗留合并：离线迁移与恢复

本版本只注册 `detect_human`，支持 `general_electric` 和 `haoda_company`，统一使用
`HumanConsumer`、`HumanConfigSchema`、`ai_camera_config_detect_human`。两个前端入口保留，摄像头列表、监控和首页计数分别限定事业部。

推测而非事实：`CameraConfigManager.ensure_feature_configs()` 会为所有摄像头补齐所有功能的默认行，

不能依据当前事业部认定旧行无效。

目前无需人工在两套不同参数中二选一。若业务人员认为该摄像头应启用人员逗留，或曾配置过其他 ROI、阈值、时段，

### 认证库：路径证据及尚缺信息

已读 `auth/user_store.py:default_database_path()`、`auth/auth.py:get_auth_users_database_path()`：优先取进程环境的 `AUTH_USERS_DB`，
否则按认证模块实际文件位置计算项目下的 `runtime/auth/auth_users.db`。相对环境路径还受进程工作目录影响，不能套用另一个 checkout 的默认目录。
`unified_backend/run_server.py:_load_env_file()` 和 `AiVision/main.py:_load_env_file()` 分别加载各自模块旁的 `.env`，`override=False`，已注入的进程环境优先。
`scripts/start.sh` 加载可选 `scripts/cold_start.env`，从项目根启动两个模块并注入共享 `AUTH_SECRET`；没有自动指定 `AUTH_USERS_DB`。

现场结果：

- V3 的 `unified_backend/.env`、`AiVision/.env` 均没有 `AUTH_USERS_DB`；`scripts/cold_start.env` 不存在。
- V3 推导出的默认路径 `/usr/zyy/Fuda_CVPreject_V3/runtime/auth/auth_users.db` 不存在，**它不是已确认的生产认证库**。
- `/etc/systemd/system/fuda-unified-backend.service` 实际配置的工作目录是 `/usr/zyy/Fuda_CVPreject_edge_work`，
  启动命令为 `python3 -m unified_backend.run_server --host 127.0.0.1 --port 5000`。只读状态显示 `MainPID=0`、`activating/auto-restart`，
  没有 drop-in；该部署目录的认证模块、`.env`、默认库当前均不可读取。这不能证明它是 V3 当前使用的认证库。
- 另一个可见统一后端进程工作目录是 `/usr/hhh.before-symlink/Fuda_CVPreject`，启动环境未设置 `AUTH_USERS_DB`；
  其代码及默认库也不可读取。`/proc/<pid>/environ` 只证明启动环境，不能排除 Python 随后加载的 `.env` 覆盖来源。

缺少的是：**V3 对外服务对应的实际进程/容器/服务标识、其可读部署代码与环境来源，以及该进程使用的认证 SQLite 绝对路径**。
因此生产用户总数、含旧标识记录数、需转换记录数均为**未核实**，不能填写 0，也没有创建空库或借用其他库继续迁移。

当前代码的权限模型是 `auth_users.role` + `departments` JSON 数组，没有功能级权限字段。
在这一已知结构下，合并不修改任何账号、角色或事业部；皓达 viewer 仍只访问皓达，通用电气 viewer 仍只访问通用电气，
双事业部 viewer 保持两者，管理员保持原权限。脚本成功核查后才报告认证旧引用与转换数为 0。
若实际库存在旧功能 ACL、旧标识出现在部门数组或其他表，脚本按表/字段报告命中行数后阻断，不能把功能名直接替换进事业部数组。
必须先确认实际权限字段语义、冲突与收缩/扩张影响，再补充对应迁移；当前没有实现猜测性的跨库权限写入。

本次没有执行生产数据迁移、删除生产数据或重启服务。

## 转换与冲突规则

1. 以 `camera_id` 合并，绝不按摄像头名称或公司名称选择算法。每个源行先校验完整 Schema、布尔值、唯一关联、外键及明确归属。
2. 只有业务字段符合当前 Schema 默认值且 `enable=false` 才认作默认空行；唯一额外等价项是微信关闭时空接收人的 NULL/空字符串。MySQL FLOAT 按其实际单精度表示比较默认值。
   启用、停用但保留了 ROI/阈值/报警参数的行均按非默认配置处理，不能仅凭 `enable=false` 丢弃。
3. 目标为默认空行时，复制源配置所有业务字段和时间戳，保留目标主键及摄像头关联；目标缺行时分配不冲突的新主键。
   源为默认空行时保留目标现有配置。**两边都有非默认配置，即使看起来相同，也报冲突**，不覆盖、不合并字段。
   所有源行仍原样保留在旧表和迁移备份中。
4. `function_config` 若存在旧键，保留值并转换为 `detect_human`；只支持布尔值或带布尔 `enable` 的对象，且必须与旧表开关一致。
   转换后的新键还必须与最终合并配置的 enable 一致；不能用旧的 false 覆盖普通功能的 true。
   新旧键共存、嵌套未知旧引用、启用关系矛盾一律报错。摄像头的总开关、地址、名称和部门不变。
5. 报警正式 `feature_name` 和已存在的 `event_metadata.feature_name` 转为统一标识；必须已具备明确的类型 5 和皓达归属。
   不猜测缺失归属，不转换不明的历史报警类型。保留报警主键、时间、摄像头/主体快照、图片/视频路径及其他 metadata。
   图片/视频文件名即使包含旧标识也保持不变，它们是证据路径，不是功能查询标识。
6. `ai_feature_department.feature_name` 及存在时的 `ai_function.name/config_table_name/import_path` 同步转换。
   部门关联重复、目录重名或未知结构均阻断。认证库不改；报警处置记录以 `aivision:<报警ID>` 关联，ID 不变，无需转换。
7. 扫描其他当前持久化表的字符串/JSON 列，发现未知旧功能引用时阻断；不盲目替换 JSON。
   检查配置行的外部引用、相关触发器与引用旧功能的视图。
   先前迁移的 `*__cfg_backup`、`bak_lg_*` 是历史备份，只列入报告，不改写也不删除。

遇到冲突时先保存独立数据库备份，使用只读查询对照主表归属、源/目标完整行和历史迁移记录，由数据负责人给出明确结论。
不要把非默认数据直接重置成默认值来让检查通过；不明确的数据应先保全并制定单独的、可核验的处置方案。
本脚本没有 `--force` 或跳过校验选项。

## 执行步骤

使用部署环境已安装的 Python 依赖，无需增加依赖。以下为操作员部署命令，**本次没有执行任何写操作命令**。
先通过安全环境注入方式设置 `HUMAN_MIGRATION_DATABASE_URL`（SQLAlchemy MySQL URL），不要把口令写入脚本、提交记录或终端日志。
脚本不会默认使用应用连接串。`AiVision/.env` 仍供导入项目现有 Schema 时读取应用基础设置；真正迁移目标只来自上述显式变量。

```bash
cd /usr/zyy/Fuda_CVPreject_V3/AiVision
export PYTHONPATH=..
# 以下两个路径必须换成部署环境的真实路径；备份文件必须尚不存在。
HUMAN_AUTH_DB=/actual/runtime/auth/auth_users.db
HUMAN_BACKUP=/secure/backup/human-20260915.json

# 可在停写前预查。默认动作也是 check：只读 MySQL 事务 + 只读 SQLite。
python -m AiVision.migrations.human_20260915 --check --auth-db "$HUMAN_AUTH_DB"
```

先确认真实认证库绝对路径、对应服务及业务数据库，完成两者的全量只读预查；任何一项未确认或冲突未解决，不进入写入步骤。
在维护窗口由操作员停止旧版 AiVision、统一后端及其他写入方，备份生产 MySQL、认证库、报警处置 JSON 和所用旧代码版本。认证 SQLite 使用其备份 API 或正确包含 WAL 的一致性备份，不仅复制主文件。
先前版本若尚未完成 `config_20260914` 配置结构迁移，先按该版本独立迁移流程处理，再进行本次合并。
现有旧表若没有 `DETECTION_IOU_THR/TRACK_IOU_THR` 等新列，本脚本直接拒绝。

停止写入后重新运行完整 check，确认无冲突，再执行：

```bash
python -m AiVision.migrations.human_20260915 --apply --offline \
  --auth-db "$HUMAN_AUTH_DB" --backup "$HUMAN_BACKUP"
python -m AiVision.migrations.human_20260915 --verify \
  --auth-db "$HUMAN_AUTH_DB" --backup "$HUMAN_BACKUP"
```

apply 先完成认证库存在性、完整结构、每条角色/事业部合法性、全部表旧引用扫描，以及业务库结构/引用/冲突预检查；再次核对认证数据未变化后，才以独占方式写出权限 `0600`、带校验和的前后数据镜像，再在一个事务里改行并逐表比较预期结果，完全一致才提交。
业务事务提交前再次只读核对认证摘要；认证变化则回滚业务事务。认证原始记录不写进脚本备份，只保存绝对路径和内容摘要，用于阻止换库及变化后继续操作。
不会执行表重建或删除。镜像包含功能配置、相关摄像头列、报警归属及目录引用，不包含摄像头 RTSP 地址、认证口令或模型文件。
仍应按敏感备份妥善存放，因为含有告警接收人等配置。
`--offline` 是操作员确认，脚本不会帮你停服务；必须确保没有后台任务、外部工具或另一实例并发写库。

## 旧表移除与上线核验

确认事务提交、verify 通过、备份可读取，并人工核对原皓达每台摄像头的 ROI、阈值、开关、采集间隔和报警绑定。
核对原皓达历史报警现在可按 `detect_human + haoda_company` 查询，数量、ID 和证据路径保持一致。
在仍然停写的同一维护窗口内，才允许独立执行旧表移除：

```bash
python -m AiVision.migrations.human_20260915 --drop-old --offline \
  --auth-db "$HUMAN_AUTH_DB" --backup "$HUMAN_BACKUP"
python -m AiVision.migrations.human_20260915 --verify \
  --auth-db "$HUMAN_AUTH_DB" --backup "$HUMAN_BACKUP"
```

drop-old 再次检查结构、外部外键、触发器、视图、未知引用及前后镜像，才删除 `ai_camera_config_detect_human_haoda`。
MySQL DDL 自动提交，此步骤不可用普通事务撤销。不得顺便删除其他历史备份表。
verify 对迁移涉及的表投影做完整比较；若已恢复业务写入、增加报警或修改配置，会明确阻断旧表清理/恢复，避免覆盖迁移之后的新数据。

确认数据完成后部署此版本代码，再由操作员启动服务。上线验收：

- `/api/features` 只出现一个人员逗留功能，声明两个事业部。
- 两个入口分别只列本事业部摄像头，启停或修改一台不会影响另一台。
- 分别使用两事业部 viewer 账号，请求配置、状态、画面、报警详情、列表、统计、图片/视频和处置记录；跨事业部必须拒绝。

- 人员逗留未签名的 `/api/public/alarms/<id>/image` 必须登录并具有归属权限；新通知的签名链接仅可取缩略图，具体边界及微信验收见下节。其他功能的卡片 URL 行为保持现有约定。

## 报警证据权限及微信通知

合并前，普通图片/视频路由依赖全局登录中间件，但没有逐报警事业部校验；公开图片路由不登录即可凭 ID 读取完整图片。
此前合并改动为图片、视频及公开人员图片增加了归属校验，而 `AlarmDispatcher._alarm_card_urls()` 仍生成无签名公开 URL，
`WeChatNotifier._send_news_card()` 原样把它放进 `news.articles[].picurl`。因此匿名抓图会收到 401，而已登录的跨事业部访问收到 403。
这就是缩略图退化的直接原因，不能通过恢复匿名完整证据访问来修复。
代码中早期“上传图片/降级文本+图片”的注释与当前实现不符，实际链路是平台图片 URL 图文卡片，本次同步修正这些注释。

本次保留共同报警接口的事业部检查，避免恢复已确认的直接 ID 越权；不改 guard_room、其他检测算法或其他功能卡片的公开链接约定。
人员新通知仍用现有队列、接收人配置、news 消息和详情入口，仅改缩略图 URL：

- `alarms/dispatcher.py` 在持久化得到报警 ID 后生成签名；`alarms/notifications/notification_image.py` 用 HMAC-SHA256，
  绑定专用通知用途、报警 ID、报警所属事业部及到期时间。
- 密钥复用启动脚本已向 AiVision 注入的 `AUTH_SECRET`，拒绝空值、开发默认值和不足 32 字符的值。
  默认有效期 86400 秒，可用 `WECHAT_THUMBNAIL_TTL_SECONDS` 设置为 60–604800 秒。
