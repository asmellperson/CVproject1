# 企微图文卡片与 SQL 开关解耦修复设计

## 问题

AiVision 企微报警优先发送单条 `news` 图文卡片。卡片的缩略图和详情链接依赖已保存报警记录的 `alarm_id`。提交 `00519d0` 让报警持久化严格服从 `sql.enable` 后，`sql=false`、`wechat=true` 的组合不再保存记录，导致卡片 URL 为空并降级为旧版文本消息加图片消息。

## 方案比较

1. **企微开启时保存卡片所需记录（采用）**：`wechat=true` 时同步保存并取得 `alarm_id`；只有企微和 SQL 都关闭时才不保存。改动最小，恢复原有卡片链路，同时保留单独关闭 SQL 通道的行为。
2. **强制所有开启企微的配置同时开启 SQL**：需要修改配置和界面语义，且旧数据仍可能处于不一致状态，不采用。
3. **改用不依赖报警记录的新企微消息类型**：需要重新设计图片素材、详情内容和发送协议，超出本次回归修复范围，不采用。

## 行为

- `wechat=true`、`sql=false`：调用 `save_now`，队列携带含 `id` 的报警记录，发送单条图文卡片。
- `wechat=true`、`sql=true`：保持现有同步保存和图文卡片行为。
- `wechat=false`、`sql=true`：保持现有异步 SQL 写入行为。
- `wechat=false`、`sql=false`：不保存报警记录，不发送企微。
- 同步保存失败时保留现有降级策略，并记录现有错误日志，不在本次修改中扩大故障处理范围。

## 修改范围

- `AiVision/core/alarm/dispatcher.py`：将持久化条件改为“SQL 开启或企微需要图文卡片记录”。
- `AiVision/tests/test_wechat_news_card.py`：增加 `sql=false`、`wechat=true` 回归测试。
- 不修改企微消息样式、前端报警页面、数据库结构、配置接口或其他报警通道。
